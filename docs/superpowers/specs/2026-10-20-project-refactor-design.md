# TrafArch 全项目重构设计

状态：用户已批准直接实施，执行细节由执行者决定。日期：2026-10-20；2026-10-21 根据用户完整测试与源码 / APK 交付授权更新验收范围。

## 1. 用户目标与工作边界

用户要求重构整个项目的代码结构、文件结构，并解决早期临时接入读卡识途
（Trip Reader）在线数据的历史遗留问题。用户已明确选择：
**彻底移除运行时依赖，使用项目自有本地数据和导入工具。**

本设计覆盖 Dart 应用、Android 平台桥接、参考数据库及离线维护工具、归档、
设置、读卡和展示之间的职责关系。不能只移动文件、拆成 part 文件，或只修 lint。
目标是在现有读卡功能的基础上建立可独立维护的模块、可追溯的数据构建流程和安全的升级迁移。

沿用 Flutter/Dart、Android Kotlin、SQLite/Drift；不借此更换 UI 框架或重新设计产品外观。
这属于执行者的技术选择。离线导入首先交付开发者 CLI；手机端不新增联网下载器。
现有用户主动打开的反馈网页、致谢来源链接、可选系统扫码服务不属于参考数据依赖，继续保留。

当前验收范围：运行全量自动化测试、Android / Kotlin 编译及 APK 构建，检查数据完整性、
源码 / 补丁 / APK 一致性并交付实卡测试包。2026-10-21 的新授权覆盖早先取消测试的限制；
先前报告中的禁测文字仅说明当时范围。真实设备安装、启动与实卡验证尚未执行，须准确标明。
不固定减去 800 分掩盖上海余额问题；不将静态检查宣称为实卡问题已经修复。
未经用户另行要求，不推送、发布或替开发者发送消息。

## 2. 当前基线与已查明问题

基线为 `8a4818e7d4dc848432a3e39a69195255138a3b95` 加本地 6 个文件的漏合修复。
本地源码已做完整 ZIP 备份。当前静态结果为 0 error、0 warning、43 info。

- 当前 `KnowledgeBase.load` 已经只加载本地 JSON 和两个 SQLite；没有发现仍在执行的
  Trip Reader HTTP 下载。遗留问题是旧格式模型、错误文档、运行时来源适配和不完整查询。
- `parseTripreaderDatasetCsv` 无调用者，仍与站点查询放在产品代码里。
- CU 启动时重建 `kb_*` 索引，只保留显示名；原始线路字段和公交字典未进入查询结果。
- TU 用户站点覆盖/未知记录写在可被资产更新覆盖的参考库中，存在升级丢数据风险。
- TU/CU 城市码与候选查询混用；CU 类型/地区约束不完整时也可能匹配，存在误报风险。
  已核实 `1210` 在 TU 中是石家庄、在 CU 中是锦州，不能按编码字符串合并为同一个城市。
- `AppState` 有 1,175 行，负责平台通道、会话、知识库、扫码、设置、归档和日志。
  专家页 1,354 行，多个数据文件超过 800 行。
- 档案历史迁移存在字段不一致：旧迁移把 card_number_masked 改名为 card_number，
  但当前模型与生成映射仍包含两列。v5 又未先把旧快照转入批次，首次新保存可能覆盖旧历史。
- 已枚举 156 个非生成 Dart 文件、452 条内部依赖，未检测到 import/export 环。
  重构主要针对职责和语义，不以不存在的循环依赖作为理由。

审计证据存于工作区 `work/refactor-20261020/`：数据与状态审计、数据库清单、依赖清单，
以及并行的协议/平台和界面/归档审计。后续修订以当前源码和审计证据为准。

## 3. 目标模块结构

  app/                            # 依赖装配、根组件、导航、主题、版本

    transit/
      tunion/                     # TU 数据模型、文件读取与解码
      city_union/                 # CU 数据模型、文件读取与解码
      local/                      # 北京等城市特例、上海双应用编排
      qr/                         # JT/T 1179 数据解析
    bank/                         # EMV/PBOC 发现、读取、TLV 与领域模型

  platform/

    storage/                      # 目录、设置文件、日志导出

    scan/application/             # 读取协调器与 ScanController
    reference_data/domain/        # 数据契约、命名空间、匹配证据
    reference_data/data/          # 只读 SQLite 与用户覆盖数据库
    reference_data/application/   # ReferenceDataController / 查询服务
    reference_data/presentation/  # 数据版本、来源、覆盖范围和加载错误
    transit_analysis/             # 行程重建、卡识别、分析结果
    archive/                      # 档案领域、应用服务、Drift 持久化
    settings/                     # 设置控制器与页面
    qr/                           # 扫码获取、QR 会话与页面
    home/                         # 交通卡/银行卡/FeliCa/二维码独立面板
    expert/                       # 协议文件、原始记录、日志等独立视图
    trips/                        # 行程展示组件与格式化映射

    bank_card/presentation/       # 银行卡详情页面
  shared/                         # 少量确实跨模块的格式化与展示组件

目录是目标职责映射。实现时可将过小文件合并、将复杂子模块进一步拆分，但不得退回
一个无边界的 core/data 或上千行 AppState。新工具必须可进入版本控制，修正当前忽略整个
`/tool/` 的规则；生成文件/本机配置继续忽略。

依赖方向：展示调用应用服务，应用服务使用纯领域契约，平台/SQLite 提供适配器，
`app` 统一装配。协议解析器不导入页面、AppState 或 SQLite；页面不拼 SQL 或解释 APDU 字节。
解析结果与格式化后的 UI 文案分离。迁移完成后更新所有引用和测试路径，不保留整套旧路径
转发文件作为永久双轨结构。

## 4. 本地参考数据与导入流程

### 4.1 数据所有权与完整性

“项目自有”指由项目维护版本、导入规则和发布产物；不得抹去第三方数据的历史来源和致谢。
原始来源快照不可覆盖。TU/CU 始终是两个独立文件，CU 查询不能要求 TU 库同时存在。
按地区分表的原始结构、跨地区字典、全部来源记录保留；允许离线追加稳定查询视图和索引。

必须完整保留 `source_field`、`source_key`、`raw_value_json`、`record_provenance`、
CU `line_key`、`line_code`、`line_number`、`station_code` 及规则上下文。
原始标识始终为字符串，不因排序、CSV 解析或数字转换丢失前导零。
显示线路名不能取代原始线路码；无法确认的值保持空/未知。
基线两库 `integrity_check` 均为 ok、外键违规均为 0，逐表内容摘要已存于
`work/refactor-20261020/baseline-data-content.json`，供迁移后逐项核对。

基线最低完整性指标（不是随意裁剪目标）：

| 数据 | 基线 |
|---|---:|
| TU 地区 | 40 |
| TU all_records | 7,480 |
| TU bus / brt | 1,708 / 227 |
| CU 地区 / 站点 | 7 / 1,732 |
| CU terminal_index | 6,111 |
| CU routes | 171 |
| CU bus_routes | 13,852 |
| CU cu_prefix_dictionary | 1,122 |

导入不得仅核对总数：必须比较原始字段、稳定主键、逐表/逐行内容及来源哈希；
新增数据可使计数上升，删除/冲突必须输出明确差异并拒绝静默覆盖。

### 4.2 离线工具

开发者在本地执行 Python 标准库 CLI，提供 `inspect`、`build`、`validate`、
`import-csv`、`diff` 子命令。输入只能是本地清单与文件，不接受 URL 或自动下载。
旧 Trip Reader CSV 的兼容解析只放在导入工具；运行时不保留 CSV 加载/解析入口。

导入将 TU 前缀表、JSON 补充卡片元数据和 CU 字典的优先级写进配置与产物清单。
不同来源冲突、未命名条目、无法归属地区的记录独立列出，不猜测或自动跨城合并。
原始 SQL 表和 JSON 数据都要能从清单追溯。所有运行时必要的卡片元数据发布在
TU/CU 数据包或明确版本化的本地产物中，不在启动时重新合并上游格式。

构建在临时文件中完成，校验成功后原子替换产物；失败保留已有可用版本。
同一输入和工具版本产生可复现内容及清单，不写本机绝对路径或当前随机时间作为内容键。
索引构建在开发者工具中完成，手机启动只做校验、安装和只读查询。

### 4.3 运行时安装与生命周期

参考数据以内容版本命名安装文件，通过清单检查协议、格式、哈希、必要表/字段。
只读打开；不在包文件里写索引、用户覆盖或未知站点报告。
加载错误通过独立状态显示“某数据源不可用”，继续保留原始读卡结果，不伪装成完整空库。
依赖装配层拥有句柄，初始化合并并发请求，销毁时明确关闭；移除全局 TuDatabase 单例。

### 4.4 用户数据迁移

用户站点覆盖和未知记录存入独立的 `reference_user.sqlite`，与只读资产及卡片档案分离。
首次升级从旧 `trafarch_db/trafarch_database_tu.sqlite` 中读取
`tu_user_station_overrides` / `tu_unknown_station_reports`；在事务内迁移，
以稳定键和迁移标记保证可重入。保留原始时间、计数和字段。
迁移失败保留旧库与错误状态；不删源文件、不覆盖用户数据；旧版本没有表时正常建立空库。
用户新数据优先，不让重复启动或较旧的来源覆盖新记录。
卡片档案数据库名称、既有身份/指纹与快照 v1/v2 的读取兼容保持；结构移动不触发清空。
档案 schema 升至 v6，仅做增量兼容修复：按实际列检查补齐 nullable 的
`card_number_masked` 兼容列，不从脱敏值拼造完整卡号；在任何新写入前，将仍存在的
旧 `session_data_json` 幂等转存为有来源标记的批次，保留无法解析的原文。
已经被旧版本覆盖掉的数据不能伪称恢复。指纹和自定义名称不因重构重新生成。

新的快照格式 v3 记录读取上下文、币种/金额单位、原始记录、完整已知原始字段和
单条解析/匹配来源；旧 v1/v2 经独立适配器读取，缺失字段保持未知。
严格分派版本；未来版本/损坏内容返回可见诊断并保留原文，不冒充 v2、静默丢弃或回写删减结果。
批次原始证据与显示投影分离，不以“最大解析版本”冒充所有条目均已升级。
详情和文本导出使用同一 `ArchiveHistory` 查询，包含所有批次和过程记录；显示上下文来自
该档案而非当前贴卡会话。部分读取不清空之前已观察到的卡号/余额，但本次缺失需显示为缺失。

## 5. 查询语义和数据接口

查询入口必须显式区分 TU、CU 命名空间和城市代码。跨城市查询只能由明确的查询 API
请求，不能作为普通读卡解析的隐式兜底。返回命中、歧义、未知或不可用，以及原始候选和来源。

- TU 保留按 source_key/source_field/transport_type 的精确匹配、HEX 片段、过程记录
  和北京公交编码规则；文本格式变化不能改变原始查询键。
- CU 直接查询完整 terminal_index / station_lookup、routes、cu_prefix_dictionary 和
  bus_routes，不把内部 station_id 当卡内编码；匹配结果携带原始线路和站点编码。
- CU 规则指定地区或交易上下文时，缺失上下文不能视作满足条件；同优先级候选含不同
  站点时返回歧义，不取列表第一项。
- 深圳历史公交映射必须同时满足 region=5180、正确解码的 carrier/type=1、显式启用
  线路查询、站点未命中、交易时间 `< 1735675200000`。缺日期/类型时保持未匹配。
- CJ/T 331 的交易指令类型 0x06/0x09 与旧规则的 decoded carrier/type 分开建模，
  不直接互传。只有现有解析器可证明的上下文才启用对应规则；未知字段照样保留。
- 数据概况页分别展示 TU/CU 版本、来源、站点覆盖、公交字典和加载/迁移状态，
  不再把空 Map 当作已加载数据集。

## 6. 应用会话、协议和界面重构

`AppState` 的职责迁移到协作对象：

- `ScanController` 管理扫描阶段、世代号、进度、取消和当前结果。
- `CardReadCoordinator` 装配并调用 TU/CU/地方卡/银行卡/FeliCa 读取器，返回类型化结果，
  不用 Object 加强制转换连接不同协议。
- `ReferenceDataController` 管理参考数据状态与查询服务。
- `QrController` 管理解码和本次二维码结果；`SettingsController` 管理设置加载/写入。
- `ArchiveController` 管理待保存、确认、自动保存、历史批次和用户自定义名称。
- 日志和导出服务独立；根依赖对象集中负责创建与释放。

会话只能由同一世代更新；停止/换卡/dispose 后旧异步任务不能覆盖新结果、继续通知或
关闭新连接。已读到的原始数据及部分成功结果有明确归属，不在跨协议异常时无条件丢失。
保存弹窗绑定具体 pendingSaveId，确认/取消必须针对该 ID，不操作换卡后出现的新待保存记录。
余额字段保持“未读到”和合法 0 的区分，TU/CU 分钱包，Suica 交易后残高不混作交易金额。

协议按家族组织，通用 APDU/TLV/只读约束提取成有明确契约的组件，保留已有协议差异，
不为代码相似而强行统一不同含义的字段。原生 MainActivity 拆分 NFC 会话/通道、
扫码、导出等处理器；保持 MethodChannel 名称、消息结构、权限和包名兼容。

主页各卡片面板、专家页各协议文件视图、行程条目和格式化映射成为独立组件。
不通过 mixin/part 把同一个巨型可变对象藏到多个文件。
卡片详情加载失败和空结果分开显示；跨批次归档合并留在档案应用层而非 Widget build。
移除 release 中临时输出原始异常的 ErrorWidget，改为可理解的错误页和受控诊断记录。

已有八达通余额/历史服务未实现、银行卡/FeliCa 会话归档策略等能力边界必须明确保留，
不因目录重构虚构新的读卡能力，也不把尚未验证的实卡问题写成已解决。

完成审计必须覆盖全部目标，而不是以某一小阶段通过替代全项目完成：

3. 产品代码无 Trip Reader 在线下载/旧 CSV 加载；文档和界面准确描述离线数据。
4. 工具能从冻结本地来源构建两个独立包，校验清单、数据量、原始字段、规则和完整性；
   证明 CU 单库包含其全部查询数据，新增/冲突/失败行为有可审阅证据。

8. 导出完整源码、可应用补丁、数据工具说明、架构文档、变更/迁移报告、文件清单和哈希。
